# M10 — Extended device library: implementation plan and tracker

Shared tracking file for GitHub milestone **M10 — Extended device library**
(milestone 11). Status lives in the checkboxes and the tracker table below; tick
an item only when it is merged with green validation and, where observable from
a deck, a C-golden comparison. Detailed cross-milestone status still belongs in
[TODO.md](../../TODO.md); update it as each slice lands.

- Base: `main` after the v0.4.0 / M9 merge (`work/m9` at `39bc85a`).
- Work branch convention: `work/m10-<slice>` (e.g. `work/m10-jfet`).
- Fixture convention: `conformance/netlists/m10_<device>_<analysis>.cir` with
  goldens captured deliberately via `cargo xtask golden capture` and reviewed.
- No full SPICE parity is claimed for any device; every unported level,
  parameter or flag fails with `SpiceError::NotYetPorted` naming its C file.

## Wave 0.5 — performance pass

Goal: remove the super-linear costs found by the [baseline](#performance-baseline)
before new devices (especially the T-line's transient history) are built on
them.

**Decision (proposed, from the experiments below): adopt the native SPARSE 1.3
solver, drop faer and diffsol, and adopt C's linear-solver error policy.**
The prototype (`proto/native-solver`, `5516457`, see
`docs/port/NATIVE_SOLVER_PROTOTYPE.md` on that branch) and a faer control
(`proto/faer-control`, uncommitted worktree) showed:

- The baseline slowdown was our own wrapper code: the n-solve rank probe,
  residual checks, Newton equilibration, fresh factorizations, an O(n²) node
  table clone and per-load allocations. Removing it gives the speedup with
  either solver (2× to over 138× in instructions retired).
- With that overhead removed, faer and SPARSE are within 4% on `.op`/`.dc`/MOS
  decks. SPARSE is 12–24% faster on linear transients and `.ac` (it refactors
  with the previous pivot order; faer redoes partial pivoting every time). faer
  is 2× faster on the 10k-node 2D resistor mesh, and on a 50k-node mesh needs
  4.7× fewer instructions and 70× less CPU time
  ([quiet-machine table](#after-wave-05-2026-10-12)): Markowitz fill grows
  much faster than faer's COLAMD/supernodal fill there.
- SPARSE is chosen for fidelity to C (pivot order, error semantics, the
  `.pz` determinant search), and because it cuts the lockfile from about 200
  packages to 18. Its speed edge is modest.
- Bound-pattern stamping saves 8–14% on transient decks with either solver.
- After the change, the solver is 4% of MOS transient time (device load is
  81%) and 14–25% of `.ac` time (`ComplexMatrix::from_operators` is 45–75%).

Exit: on the baseline decks, `ladder1000_ac` and `ladder1000_tran` within 5x of C,
`ladder10000_op` within 3x, no `.ac`/`.tran` timeouts at 10k nodes, all
production goldens unchanged, no tolerances loosened without a C reference.

### Status (2026-10-12, draft PR #137 `wip/native-solver-fidelity` -> `work/m10`)

The native solver line is integrated with `work/m10` (PR #137 contains
`origin/work/m10` at 972fa30, so it merges as a fast-forward of that line).
Fidelity is measured per vector against a `-ffp-contract=off` C build (C fuses
multiply-adds otherwise): 126 of 138 conformance decks are bit-identical
(134 with `wip/fid-jfet`);
`epoly_dc`/`gtable_dc` need XSPICE code models the reference build lacks.
Validation: fmt, clippy and tests on stable and 1.89, `golden verify` (137
verified, 1 unsupported: `multi_analysis_pz`), all live-C suites.

- **0.5a done.** Degenerate decks (source loops, floating nodes, current-source
  cutsets, near-singular, badly scaled, zero R/C/L) give C's answer or C's
  class of error naming the same unknown (`tests/solver_robustness.rs`).
  C's `spSMALL_PIVOT` is silent; the port warns. Gaps: `optran.c` (C's
  transient operating-point fallback) is not ported, so decks C rescues that
  way fail explicitly; zero/negative `.model` C/L values are still rejected.
  The repository-root `AGENTS.md` guardrail update is pending: that file is
  not tracked on this line.
- **0.5c done.** `.pz` builds and loads its matrix as `CKTpzSetup`/`CKTpzLoad`
  do, and the Muller search is bit-identical. On `multi_analysis_pz` the
  no-FMA C build hits the iteration limit (no poles) while the FMA build
  finds 3; the port matches the former, so the golden (captured with the FMA
  build) stays unsupported.
- **0.5d.** Merge done: MOS1 is the exact `mos1load.c` port and the shared
  MOS shell (MOS3, binning) is rebuilt on it; diffsol is removed
  (`backend=diffsol` is an explicit error); T-line breakpoints go through C's
  breakpoint table (`TRAaccept` -> `CKTsetBreak`). The quiet-machine
  benchmark is [recorded below](#after-wave-05-2026-10-12); every exit
  criterion holds. The faer control is committed on the local branch
  `proto/faer-control` (`c620425`, on `work/m9`) as evidence.
- **0.5h done.** Card budget 1,000,000 (with the 250,000-device expansion
  budget); diode chains of 10–1000 stages and `inv201_tran` are bit-identical
  to C (new deck `diode100_op`).
- **M10 device fidelity: JFET/JFET2 done** (`wip/fid-jfet`). Both loads are
  operation-by-operation ports of `jfetload.c`/`jfet2load.c` (C's state
  layout, the in-load `cghat`/`cdhat` convergence test, `MODEINITPRED`/
  `MODEINITTRAN`, C's stamps; level 2 keeps C's matrix without the `CDS`
  conductance or Statz cross terms) and of `jfetacld.c`/`jfet2acld.c`, with
  `jfettemp.c`'s rounding order; all eight `m10_jfet*` decks are
  bit-identical, so 134 of 138 decks are. An `off` instance in
  `MODEINITFIX` keeps a convergence rule C does not have, because C reaches
  that operating point only through the unported `optran.c` (agreement with
  C about 1e-9, `tests/jfet.rs`). Still open, worst ulp vs the no-FMA
  oracle: `m10_tline_ac` 256, `m10_urc_diode_tran` 4e9 (time grid differs).
  Likely causes: URC's generated diodes; `traacld.c` grouping. MOS3
  `.disto`/`.sens` are explicit errors.
- **Known small divergences, no deck exposes them:** the diode breakdown
  iteration uses 1e-3 instead of `reltol`; plain `.ac` applies a capacitor/
  inductor `m` in a different order from C; the MOS1 small-signal bias does not
  reproduce C when the operating point clamped a voltage; B-source `temper`
  skips C's Kelvin round trip; state is not carried over after a transient.

How fidelity work is done (tools are not in the repository): build C ngspice
with `-ffp-contract=off` plus a trace of each matrix load, RHS, pivot and
solve; add the same trace temporarily to the port; compare decks vector by
vector in ulps and find the first differing load. Port C's arithmetic
operation by operation; never loosen tolerances or recapture goldens.

### 0.5e — device-load cost (MOS)

- [x] Drop the extra reload per converged point (residual check and charge
      recording) that C's `NIiter` does not do: 10,400 loads vs C's 8,110
      iterations on the 102-FET deck. Already gone on the branch head:
      counted 2026-10-13, `inv201_tran` makes 26,751 loads against C's 26,851
      total iterations (`.options acct`); the whole gap is the cost of a load
      (2.7M instructions against C's 0.56M).
- [x] Move per-call `finite` validation off the per-iteration path. The
      checks stay (they are a few compares once inlined); their error
      construction moved into `#[cold]` helpers (`DeviceState::set`,
      `Coefficients::integrate`, `junction_companion`, `Vector::add_to`) so
      the hot paths inline.
- [x] Remove the remaining per-load allocations and reduce
      `SparseMatrix::add` / `Pattern::find` bookkeeping (about 20% of MOS time):
      - `truncation_limit` no longer allocates a charge `Vec` per slot per
        trial; each device's truncation slots are resolved once per run.
      - MOS1/MOS3 cache their temperature derivation (`MOSxtemp`), which
        every load recomputed (with its `log`/`exp`) and which depends only
        on the circuit and nominal temperatures.
      - `SparseMatrix::add` takes a replay fast path when the stamp is the
        device's next traced element.
      - Fixed stamp batches (C's `TSTALLOC` pointers): a MOSFET stamps its 22
        elements through `StampContext::stamp_fixed`. Once a load has
        verified the batch against the pattern's recorded stamp sequence,
        later loads add the values by element (`SparseMatrix::add_fixed`),
        skipping node-row lookups and per-stamp trace checks; the matrix
        receives the same additions in the same order. Verifications belong
        to the circuit, are tied to the exact trace (`Arc`) they were made
        against, and are forgotten when devices or numbering change
        (`tests/fixed_stamps.rs`, `maths::sparse` unit tests).
      Every rawfile of the bench decks is byte-identical to the 0.5g head.
- [x] Target: MOS1 inverter decks within 3x of C (currently 6–7x). Measured
      2026-10-13 (`bench.py`, 7 runs, busy machine): `inv201_tran` 2.6x and
      `inv51_tran` 2.4x C wall time (5.4x and 5.3x before); instructions
      102.1G → 43.7G on `inv201_tran` (C 15.1G). Other decks:
      `ladder100_tran_long` 3.4x → 2.4x, `ladder1000_tran` 24.7G → 15.4G

  changes, slower after them); batching stamps without verification (no

The 0.5 exit criteria hold on the PR head (`bench.py`, median wall time):
`ladder1000_ac` 1.4x C, `ladder1000_tran` 3.3x, `ladder10000_op` 2.5x, and
`ladder10000_ac` (1.6x) finishes. Every output agrees with the C build

normalized): these are bit-identical to the no-FMA C build, and the FMA C
build alone reproduces the difference, so the chains' converged point is
sensitive to rounding inside the Newton tolerance.

Readings:

- **faer on 2D meshes.** The faer control needs 0.32x C's instructions on
  the 50k-node mesh (0.56 s CPU against C's 33 s and the SPARSE port's 40 s;
  outputs agree with C to 5.6e-11) and 0.80x at 10k nodes: its COLAMD
  ordering and supernodal LU fill far less than Markowitz ordering. SPARSE
  stays the choice for fidelity to C, but a faer ordering is the lever if
  large meshes matter.
- **`.dc` and `.op` on the PR head: not a regression of the load.** The
  prototype swept linear circuits by factoring once and updating only the
  RHS (1001 solves on `ladder1000_dc`); `94a7004` replaced that with C's
  `dctrcurv.c` loop, which runs `NIiter` (two full load/factor/solve
  iterations) at every point, as C's 2003 "Total iterations" confirm. The
  gap is the cost per iteration: about 1.8M instructions against C's 245k
  (loads 63%, factor and solve 21%), the same overhead that puts linear
  transients at 6–7x on both builds; it is 0.5e's target. `solve_ni` now
  reuses the factors when a load's values, `diag_gmin` and pivot thresholds
  equal those of its last clean refactorization (identical inputs refactor
  bit for bit): 11% fewer instructions on `ladder1000_dc`, 6–7% on the
  linear transients, outputs unchanged (`tests/factor_reuse.rs` pins the
  reuse and its invalidations).
- The PR head needs 2.6–3.1x fewer instructions than the prototype on
  `.ac` (bound complex assembly) and 12–16% fewer on MOS transients.

**Solver note (faer/diffsol).** The slowdown was not caused by the solver
libraries. In the baseline profiles faer's numeric factorization was under 1%
of samples; the time was the rank probe, residual `hypot` and allocations, and
diffsol was not used at all (`.tran` defaults to the companion driver). The
faer control experiment confirmed this: with our overhead removed, faer comes
within 1–24% of the SPARSE port, and beats it 2× on the 2D mesh. Wave 0.5
nevertheless proposes SPARSE for fidelity to C and the smaller dependency tree;
see the decision at the top of [wave 0.5](#wave-05--performance-pass). KLU stays
out: it is LGPL and would need FFI.
